# Frontend UI Engineering

## Overview

Build user interfaces that are accessible, performant and visually polished — UI that looks like it was built by a design-aware engineer, not generated by an AI. That means real design-system adherence, proper accessibility, deliberate interaction patterns and no generic "AI aesthetic".

Lint already enforces the hard rules (design-system components instead of raw HTML, design tokens only, jsx-a11y, no data fetching in `ui/`, slice boundaries). This skill covers the judgment calls lint can't make. Architecture and folder rules are in `docs/README.md`.

## When to Use

- Building new UI components, sections or pages
- Modifying existing user-facing interfaces
- Implementing responsive layouts
- Adding interactivity or state management
- Choosing or adding colors (read `references/color-palette.md` first)
- Fixing visual or UX issues

## Component Patterns

**Build from the design system.** Use the atoms in `src/features/ui/` — `Heading` (pick a `variant` and the semantic `as` level), `Paragraph`, `Span`, `Button` (variants and sizes live in `buttonVariants`), `Input`, `Select`, `Checkbox`, `List`, `Dialog`/`Modal`, `Separator` — and `Image` from `next/image`. Check what exists before writing a new component.

**Prefer composition over configuration:**

```tsx
// Good: composable
<OrdersLayout header={<OrdersHeader total={orders.length} />}>
  <OrdersGridSection orders={orders} onOpenDetails={setSelectedOrder} />
</OrdersLayout>

// Avoid: over-configured
<OrdersPage title="Orders" headerVariant="large" bodyPadding="md" content={orders} />
```

**Keep components focused.** One job per component; a component past ~200 lines should be split. A component used by a single section lives in that section's folder; `ui/components/` is for components shared by several sections or other slices.

**Separate data from presentation.** A container gets data from a hook (`src/shared/queries/*` or the slice's `lib/hooks/`), handles every state, and passes plain data down. `src/features/orders/ui/OrdersContent.tsx` is the reference:

```tsx
// Container: data and states
export default function OrdersContent() {
  const t = useTranslations("orders.content");
  const { data: user } = useUser();
  const { data: orders = [], isLoading, isError, refetch } = useOrders(user?.id);

  if (isError) return <OrdersErrorState onRetry={refetch} />;
  if (isLoading) return <OrdersLoadingSection />;
  if (orders.length === 0) return <OrdersEmptySection />;

  return <OrdersGridSection orders={orders} />;
}

// Presentation: rendering only
export function OrdersGridSection({ orders }: PropsI) {
  return (
    <List className="grid gap-6">
      {orders.map((order) => (
        <OrderCard key={order.id} order={order} />
      ))}
    </List>
  );
}
```

**Copy comes from `next-intl`.** Customer-facing strings live in `src/i18n/messages/en.json` and are read with `useTranslations`; never hardcode them in components.

## State Management

Choose the simplest approach that works:

```
Local state (useState)                  → Component-specific UI state
Lifted state                            → Shared between 2–3 sibling components
Context (src/providers)                 → Theme, auth, locale (read-heavy, write-rare)
URL state (searchParams)                → Filters, pagination, shareable UI state
Server state (React Query hooks in      → Remote data with caching
  src/shared/queries)
Zustand store (lib/stores)              → Complex client state shared across a flow
                                          (e.g. stampFlowStore)
```

Avoid prop drilling deeper than 3 levels. If props pass through components that don't use them, introduce context or restructure the tree.

## Design System Adherence

### Avoid the AI Aesthetic

| AI default                       | Why it is a problem                                                                     | Production quality                                   |
| -------------------------------- | --------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| Purple/indigo everything         | Models default to "safe" palettes, so every app looks identical                         | The stamp palette (chocolate, gold, cream)           |
| Excessive gradients              | Visual noise that clashes with the design system                                        | Flat surfaces, gradients only where the design has them |
| Rounded everything (rounded-2xl) | Ignores the corner-radius hierarchy; this brand is brutalist and mostly square          | The radii the design system uses                     |
| Generic hero sections            | Template layout with no connection to the content or user need                          | Content-first layouts                                |
| Lorem ipsum-style copy           | Hides layout problems real content reveals (length, wrapping, overflow)                 | Realistic copy from `en.json`                        |
| Oversized padding everywhere     | Equal generous padding destroys hierarchy and wastes space                              | The spacing scale, with hierarchy                    |
| Stock card grids                 | Uniform grids ignore information priority and scanning patterns                         | Purpose-driven layouts                               |
| Shadow-heavy design              | Layered shadows compete with content and slow low-end devices                           | Subtle or no shadows unless the design specifies     |

### Spacing and Layout

Use Tailwind's spacing scale (`p-4`, `gap-6`, `mt-12`). Don't invent values: `p-[13px]` and `mt-[2.3rem]` fail lint, and a value that isn't on the scale is almost always a design mistake.

### Typography

Respect the hierarchy: one `h1` per page, `h2` for sections, `h3` for subsections. Don't skip levels. Choose the `Heading` `variant` for the look and `as` for the semantics — they are independent, so never pick a heading level to get a size.

### Color

- Use tokens: Tailwind theme classes (`bg-primary`, `text-foreground`) or the stamp palette variables (`text-(--color-stamp-chocolate)`). Hex values and arbitrary color classes fail lint.
- Before adding or choosing a color, read `references/color-palette.md` — categories, where each kind of color lives, naming and the contrast-safe gold variants.
- Contrast: 4.5:1 for normal text, 3:1 for large text and UI components.
- Never rely on color alone to convey information; add an icon or text.

## Accessibility (WCAG 2.1 AA)

Every component must meet these. jsx-a11y catches the static mistakes; these are the ones it can't.

### Keyboard Navigation

Every interactive element must be reachable and usable with the keyboard. Use `Button` (or `Anchor`/`Link` for navigation) — never a clickable `div`. If a custom widget is unavoidable it needs a role, `tabIndex={0}`, and Enter/Space handling.

### Labels

```tsx
// Icon-only buttons need a label (Button warns in dev when size="icon" has none)
<Button size="icon" aria-label="Close dialog"><X /></Button>

// Form inputs need a label: FormField / Label + Input
<Label htmlFor="email">Email</Label>
<Input id="email" type="email" />

// Or aria-label when there is no visible label
<Input aria-label="Search orders" type="search" />
```

### Focus Management

Move focus when content changes: into a dialog when it opens (trap it there), back to the trigger when it closes, to the first error after a failed submit. `Dialog`/`Modal` handle trapping — don't build your own.

### Meaningful Loading, Error and Empty States

Never show a blank screen. Every data-driven view handles all three:

- **Loading:** a skeleton shaped like the content (`CartLoadingSection`, `OrdersLoadingSection`) with `aria-busy="true"` — not a spinner for content.
- **Error:** what happened, in calm blame-free copy, plus a way forward (retry button calling `refetch`).
- **Empty:** `role="status"`, what this space is for, and the next action (see `OrdersEmptySection` for the layout).

## Responsive Design

Mobile first, then expand with breakpoints:

```tsx
<List className="grid grid-cols-1 gap-4 sm:grid-cols-2 lg:grid-cols-3">
```

Check at 320px, 768px, 1024px and 1440px. The Playwright config has a mobile project for responsive tests.

## Loading and Transitions

Prefer optimistic updates for actions the user expects to be instant. Put them in the mutation hook in `src/shared/queries`, never in the component:

```ts
// Illustrative: the pattern, not an existing hook
export function useToggleFavourite() {
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: FavouritesService.toggle,
    onMutate: async (designId: string) => {
      await queryClient.cancelQueries({ queryKey: ["favourites"] });
      const previous = queryClient.getQueryData<string[]>(["favourites"]);
      queryClient.setQueryData<string[]>(["favourites"], (ids = []) =>
        ids.includes(designId) ? ids.filter((id) => id !== designId) : [...ids, designId],
      );
      return { previous };
    },
    onError: (_error, _designId, context) => {
      queryClient.setQueryData(["favourites"], context?.previous);
    },
  });
}
```

## Common Rationalizations

| Rationalization                                | Reality                                                                         |
| ---------------------------------------------- | ------------------------------------------------------------------------------- |
| "Accessibility is a nice-to-have"              | It's a legal requirement in the EU (European Accessibility Act) and a quality bar. |
| "We'll make it responsive later"               | Retrofitting responsive design is far harder than building it from the start.   |
| "The design isn't final, so I'll skip styling" | Use the design-system defaults. Unstyled UI breaks the first impression.        |
| "This is just a prototype"                     | Prototypes become production code. Build the foundation right.                  |
| "The AI aesthetic is fine for now"             | It signals low quality. Use the stamp design system from the start.             |

## Red Flags

- Components over ~200 lines
- `eslint-disable` added to get around a design-system or token rule
- Missing loading, error or empty states
- Clickable non-interactive elements, or no keyboard testing
- Color as the only indicator of state
- Generic "AI look" (purple gradients, oversized rounded cards, stock layouts)

## Verification

After building UI:

- [ ] `npm run lint` passes for the touched files
- [ ] Renders without console errors or hydration warnings
- [ ] Every interactive element works with Tab, Enter and Space; focus is visible
- [ ] Screen reader conveys the content and structure (headings in order, labels present)
- [ ] Works at 320px, 768px, 1024px and 1440px
- [ ] Loading, error and empty states all handled
- [ ] Colors, spacing and typography come from the design system
- [ ] No accessibility warnings in DevTools or axe
